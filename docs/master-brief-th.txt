ให้ใช้เอกสารนี้เป็น Master Brief สำหรับออกแบบและพัฒนาแอปทีละขั้น
ผู้ใช้จะทำงานผ่าน Codex ใน ChatGPT โดยเก็บ source code ใน GitHub repository

ผู้ใช้ต้องการให้ Codex แก้ไฟล์ใน repository, อธิบายเป็นภาษาไทย,
ทดสอบใน environment เท่าที่ทำได้ และแสดงผลเปลี่ยนแปลงให้ตรวจสอบได้

สิ่งที่ต้องแนบให้ AI พร้อมเอกสารนี้:
1. Arkham-Horror-RPG-Corebook.pdf ฉบับที่ผู้ใช้จัดเตรียม
2. โค้ดปัจจุบันของโปรเจกต์ หากเริ่มพัฒนาแล้ว
3. ผลการทดสอบหรือ error ล่าสุด หากเป็นการทำงานต่อ

เอกสารนี้เรียบเรียงจาก Master Brief ที่ผู้ใช้ให้มา เป็นข้อกำหนดของผลิตภัณฑ์
ไม่ใช่การรับรองว่าได้ตรวจสอบกฎเกมทุกข้อกับ PDF แล้ว
ค่ากฎเกมที่ระบุในหมวด RULE-CANDIDATE เป็นข้อมูลตั้งต้นจาก Brief เดิม
ต้องเปิด Corebook ตรวจสอบและบันทึกหน้าที่มา ก่อนนำไปเขียน game logic
ไม่ให้นำ citation ของแชตเดิมที่เปิดไม่ได้ไปใช้เป็นหลักฐานในโค้ดหรือฐานข้อมูล

ลำดับความสำคัญ:
- MUST / ต้อง: ข้อกำหนดบังคับ
- SHOULD / ควร: แนวทางที่คาดหวัง หากไม่ทำต้องอธิบายเหตุผล
- MAY / optional: ทำเพิ่มได้เมื่อถึงระยะที่เหมาะสม
- PROPOSED: ค่าเริ่มต้นทางเทคนิคที่เสนอ ปรับได้โดยแจ้งเหตุผล
- NEEDS_VERIFICATION: ยังต้องตรวจสอบแหล่งข้อมูล ห้ามอ้างว่าเป็นกฎยืนยันแล้ว

======================================================================
01. Product Vision และขอบเขต
======================================================================

สร้าง Private Campaign Platform สำหรับกลุ่มผู้เล่น Arkham Horror RPG
รองรับ GM, Co-GM และ Player ตั้งแต่สร้าง Campaign, เชิญสมาชิก, สร้าง
Investigator, เล่นหลาย Session, ติดตามตัวละคร, จัดการเรื่องราว, ค้นกฎ,
แปลภาษา และบันทึก Campaign ต่อเนื่อง

Core philosophy:
- Campaign is the home.
- Session is the chapter.
- Investigator belongs to the Campaign.
- Google Account identifies the player.
- Corebook defines the rules.
- Translation removes the language barrier.
- AI assists; it does not invent the rules.

GOAL-01 ข้อมูลตัวละคร, XP, Injuries, Trauma, Equipment และ Story ต่อเนื่อง
        ข้าม Session และไม่ถูก reset เมื่อจบคืนที่เล่น
GOAL-02 ผู้ใช้แต่ละคนใช้ Google Account จริง และมีหลาย Campaign/หลาย Role ได้
GOAL-03 Player ใช้งานมือถือได้คล่อง; GM เหมาะกับ Tablet/Desktop และใช้มือถือได้
GOAL-04 English/Thai อยู่บน game state เดียวกัน เปลี่ยนภาษาไม่เปลี่ยนตัวเกม
GOAL-05 กฎและ AI answer ตรวจสอบย้อนกลับถึง Corebook ได้

ขอบเขตนี้ไม่ใช่ Arkham Horror: The Card Game companion และห้ามนำกลไกของ
LCG, board game หรือระบบ Call of Cthulhu มาปะปนกับ Arkham Horror RPG

นอกขอบเขตเวอร์ชันแรก:
- Public content marketplace หรือ public rulebook library
- การแจก PDF/artwork/book content สู่สาธารณะ
- ระบบชำระเงิน, voice/video chat, virtual tabletop เต็มรูปแบบ
- Offline multiplayer หรือการรับประกัน real-time latency ระดับเกมแอ็กชัน
- ย้ายฐานข้อมูลไปบริการอื่นโดยอัตโนมัติ

02A. เครื่องมือพัฒนา: ChatGPT Codex + GitHub Codespaces
======================================================================

DEVENV-01 GitHub repository เป็น source of truth สำหรับ source code,
         documentation, schema, tests และ migration scripts
DEVENV-02 ใช้ ChatGPT Codex เป็น coding agent สำหรับอ่าน/แก้/ตรวจ repository
         โดยทำงานตาม instructions ที่เก็บใน repository เช่น AGENTS.md
DEVENV-03 ใช้ GitHub Codespaces เป็น Cloud Development Environment หลัก
         สำหรับติดตั้ง dependencies, run tests และ preview/dev server
DEVENV-04 Codespaces เป็น environment สำหรับพัฒนาและทดสอบ; ไม่ใช่ที่ host
         Google Apps Script runtime และไม่แทน Google Sheets/Drive
DEVENV-05 Production backend ยังคงเป็น Google Apps Script ตาม stack หลัก
         การ publish web app ทำผ่าน Apps Script deployment ที่กำหนดไว้
DEVENV-06 GitHub Actions อาจใช้ตรวจ format/lint/unit tests ได้เมื่อจำเป็น
         แต่ห้ามออกแบบ workflow ให้ deploy production อัตโนมัติโดยปริยาย
DEVENV-07 Repository แนะนำให้เป็น Private เพราะมี source, schema และ
         integration configuration ของแอป; ห้ามใส่ Corebook PDF หรือ
         extracted full-book text ใน repository
DEVENV-08 Commit เฉพาะ source/config ที่ไม่เป็นความลับ; ใช้ `.gitignore`
         สำหรับ `.env`, clasp credentials, local tokens, generated exports,
         uploaded scans และ temporary/cache files
DEVENV-09 Secrets ใช้ GitHub Codespaces Secrets สำหรับ development ที่จำเป็น
         และ Google Apps Script Script Properties สำหรับ runtime secrets
         เช่น GEMINI_API_KEY; secrets คนละ environment ต้องไม่แชร์ผิดที่
DEVENV-10 ห้าม echo/print secrets ใน workflow, terminal output, tests,
         screenshots, error trace หรือ Codex response
DEVENV-11 กำหนด Node.js/tool versions และ dependencies ให้ reproducible
         เช่น lockfile, `.devcontainer/devcontainer.json`, README setup
         และคำสั่ง test ที่รันได้จาก clean Codespace
DEVENV-12 ก่อนแก้ไฟล์ Codex ตรวจ branch/status/diff; ทำการเปลี่ยนแปลงเป็น
        ชุดเล็ก ตรวจ diff และทดสอบเฉพาะที่เกี่ยวข้องก่อนรายงาน
DEVENV-13 หาก repository มี AGENTS.md หรือ project instructions ให้ทำตาม
         และห้ามเขียนทับโดยไม่จำเป็น
DEVENV-14 ห้าม Codex commit/push/merge/deploy โดยอัตโนมัติ เว้นแต่ผู้ใช้
         สั่งชัดเจน; หากผู้ใช้ขอให้ทำ ให้รายงาน branch/commit/deployment ที่ทำจริง
DEVENV-15 อย่าใส่ service account key หรือ Google user credential ลง GitHub
         ให้เลือก authentication สำหรับ local/Codespaces และ clasp ตามเอกสาร
         ทางการปัจจุบัน พร้อมอธิบายการ revoke credential

Repository layout (แนวทาง ไม่ใช่ข้อบังคับให้แตกไฟล์ครบตั้งแต่ STEP 1):
  /src หรือโครงสร้างที่เข้ากับ Apps Script
  /test หรือ /tests
  /docs
  /scripts
  /.devcontainer/devcontainer.json
  /.github/workflows/ci.yml (ถ้าใช้ CI)
  .clasp.json (ห้ามเก็บ credential; คุม access ตามแนวทาง project)
  .claspignore
  .gitignore

Codex workflow ต่อหนึ่ง STEP:
1. ตรวจ project instructions, branch, working tree และไฟล์ที่เกี่ยวข้อง
2. สรุปสิ่งที่จะเปลี่ยนและ assumptions ก่อนแก้ หากเป็นงานขนาดใหญ่
3. แก้ไฟล์จริงใน repository ด้วย patch ที่เล็กและ review ได้
4. รัน formatter/linter/tests ที่มี; ถ้ารันไม่ได้ บอกเหตุผลและคำสั่งให้ผู้ใช้
5. ตรวจ diff ว่าไม่มี secret, PDF, generated dump หรือ unrelated changes
6. แจ้งไฟล์ที่เปลี่ยน, วิธีทดสอบ, ผลจริง, limitation และขั้นตอนให้ผู้ใช้ทดสอบ
7. หยุดที่ gate ของ STEP นั้น ห้ามเริ่ม STEP ถัดไปเอง

ข้อจำกัดการทดสอบ:
การทดสอบใน Codespaces ไม่รับรอง deployment, Google OAuth consent,
Apps Script scopes, Sheets/Drive permissions, quota หรือ Gemini access จริง
ต้องมี deployment smoke test แยกใน Google Apps Script ด้วยบัญชีทดสอบ
ก่อนให้ผู้เล่นใช้ และห้ามส่ง production credentials เข้า CI

ความเป็นเจ้าของข้อมูลที่ต้องอธิบายก่อนติดตั้ง:
Google Account ระบุตัวผู้ใช้ ไม่ได้หมายความว่าแต่ละ Player ต้องมีสำเนา Sheet
หรือสิทธิ์เปิด raw database ใน Drive ของตนเอง
PROPOSED: ใช้ฐานข้อมูลและ Drive folder กลางภายใต้บัญชีผู้ติดตั้ง/เจ้าของระบบ
สมาชิกเข้าถึงผ่านแอปที่ตรวจสิทธิ์ ไม่แชร์ Sheet ที่มีข้อมูลทุก Campaign
หากต้องการให้แต่ละ GM เป็นเจ้าของ storage แยกบัญชี ต้องออกแบบเพิ่มเติม
และตกลง architecture ก่อนเริ่มพัฒนา ไม่ให้ AI สมมติว่าเป็นสิ่งเดียวกัน

ก่อนเลือกวิธี Sign-In ให้พิสูจน์กับ URL deployment จริง:
- รูปแบบ deployment และบัญชีที่รัน Apps Script
- Google Cloud/OAuth configuration, authorized origins/redirects ที่จำเป็น
- ข้อจำกัดของ HTML Service/iframe/cookie/redirect ใน flow ที่เลือก
- ผู้ใช้ Google ส่วนตัวต่างบัญชีเข้าใช้งานและระบุตัวได้อย่างถูกต้อง
หากทำไม่ได้ใน stack นี้ ให้รายงานหลักฐานและเสนอทางเลือกก่อนเปลี่ยน stack

Google Account -> User -> CampaignMembership -> Campaign

MODEL-06 ประวัติ Session ที่จบแล้วต้องอ่านจาก snapshot/event history

04. Authentication และ User Profile
======================================================================

AUTH-01 Login ด้วย Google Account ก่อนเข้าถึงข้อมูลแอป
AUTH-02 ห้ามใช้ Player Name + Room Code เป็น identity หลัก
AUTH-03 ห้ามพึ่ง Session.getActiveUser().getEmail() เพียงอย่างเดียว
AUTH-04 Internal UserID อิง immutable Google subject identifier ที่ตรวจสอบแล้ว
        ห้ามเชื่อ UserID/email/role ที่ client ส่งมาโดยไม่มี verification
AUTH-05 การ decode JWT เฉย ๆ ไม่เท่ากับตรวจสอบ token
        วิธีที่ใช้ต้องยืนยันความถูกต้องของ token รวมถึง signature/issuer/
        audience/expiry ตาม Google documentation และ threat model ของ flow
AUTH-06 ใช้ verified email สำหรับ email-bound invitation
AUTH-07 ออกแบบ login expiry, logout, reauthentication และ error state ชัดเจน
AUTH-08 ไม่บันทึก raw credential/token ลง log, URLs หรือ Sheet ที่ผู้เล่นเข้าถึง
AUTH-09 หากมี app session ต้องมี expiry/revocation และ server-side validation
AUTH-10 Authentication แยกจาก Campaign Membership เสมอ

User fields:
UserID, GoogleSubjectID, Email, EmailVerified, DisplayName,
PreferredLanguage, CreatedAt, LastLoginAt
อาจใช้ GoogleSubjectID เป็น UserID โดยตรง หรือ mapping แบบ unique ที่คงที่

AC-AUTH:
- บัญชี A/B ต้องได้คนละ UserID และกลับเข้าใช้อีกครั้งได้ ID เดิม
- token ปลอม/หมดอายุ/ผิด audience ถูกปฏิเสธ
- ส่ง UserID ของคนอื่นจาก client ไม่ทำให้สวมสิทธิ์ได้
- เมื่อหมดอายุ ระบบให้ login ใหม่โดยไม่แอบทำ mutation ต่อ

05. Authorization, Roles และ Visibility
======================================================================

Role ภายใน Campaign: GM, CO_GM, PLAYER
ผู้สร้าง Campaign เป็น GM และ Campaign Owner อัตโนมัติ
Campaign Owner เป็นสิทธิ์กำกับดูแลเพิ่มเติมจาก Role

PERM-01 ทุก server operation ที่อ่าน/เขียน campaign data ต้องทำ:
        Authenticate -> Membership -> Role -> Object/Field Permission -> Execute
PERM-02 Default deny: object ใหม่ที่ยังไม่กำหนดสิทธิ์ต้องไม่เผยให้ Player
PERM-03 ตรวจสิทธิ์จากข้อมูลปัจจุบันบน server ทุก request
PERM-04 Player API ห้ามส่ง GM secrets ลง browser แม้ UI จะซ่อนได้
PERM-05 URL, file ID, record ID, search results, translations, exports และ AI
        ต้องอยู่ภายใต้สิทธิ์เดียวกับข้อมูลต้นทาง
PERM-06 การย้าย object ไปอีก Campaign ผ่านการแก้ CampaignID ต้องถูกปฏิเสธ
PERM-07 Player แก้ได้เฉพาะ Investigator ของตนและ field/action ที่อนุญาต
        ห้ามแก้ XP, approval, official costs/limits ตามใจผ่าน API
PERM-08 การถอดสมาชิกหรือเปลี่ยนสิทธิ์ต้องทำให้ request ถัดไปใช้สิทธิ์ใหม่
        และ invalidate permission-sensitive cache

Role capabilities:
GM: จัดการ Campaign, Members, Sessions, Characters, Story และ GM data
Co-GM: ช่วยจัดการ Sessions/Story/Characters และอ่าน GM data ตาม visibility
Player: อ่าน player-safe data, จัดการ character ของตนตาม workflow, เล่น/ทอย
Owner only (PROPOSED): transfer ownership, archive/delete Campaign,
                       แต่งตั้ง/ถอด GM หรือ Co-GM และ ownership settings
ห้าม Co-GM ยกระดับสิทธิ์ตนเอง; ปรับขอบเขตได้หากเจ้าของระบบสั่งชัดเจน

Visibility enum และความหมายเริ่มต้น:
GM_ONLY: GM เท่านั้น
CO_GM: GM และ Co-GM
CAMPAIGN_PLAYERS: ACTIVE members ทุก Role ใน Campaign
SELECTED_PLAYERS: ผู้เล่นที่เลือกด้วย UserID พร้อม GM/Co-GM ที่มีสิทธิ์จัดการ
PUBLIC: สงวนสำหรับข้อมูลที่ตั้งใจเผยแพร่; ปิด public access ในรุ่นแรก
        ค่า PUBLIC ไม่ใช่ทางลัดข้าม authentication และไม่ใช้กับ Corebook
UI ควรใช้ชื่อ "GM + Co-GM" สำหรับ CO_GM เพื่อไม่ให้เข้าใจว่าตัด GM ออก

Field-level example:
NPC.PublicName = Professor Morgan
NPC.PlayerInformation = He seems nervous.
NPC.GMSecret = He belongs to the cult.
Player response ต้องไม่มี key/value GMSecret รวมถึงใน nested JSON และ AI context

Private notes ของ Player เป็น owner-only โดยค่าเริ่มต้น; ผู้ใช้เลือก share ได้
GM private notes กำหนด GM_ONLY หรือ CO_GM ให้ชัดเจน

- หากทำงานหลาย write ไม่ครบ ต้อง recover ได้ และไม่ประกาศ COMPLETED

Timeline แสดง Session 01, 02, 03... พร้อมเปิดดู summary/events/clues/NPCs/

RULE-07 Player View Original ต้องไม่เปิด full PDF ที่มี GM content โดยอัตโนมัติ
        ใช้ permitted excerpt/page view ที่ผ่านการตรวจ spoiler หรือไม่เปิดปุ่ม

AI-01 Flow: Question -> Permission-filtered retrieval -> Relevant source
      -> Gemini -> Validated answer -> Source citations
AI-02 กรองสิทธิ์ก่อนส่ง context ให้โมเดล ไม่ส่ง GM secret แล้วหวังให้ AI ซ่อนเอง
AI-03 ผลตอบแยก OFFICIAL RULE / EXPLANATION / AI SUGGESTION
AI-04 Official claims ต้องเชื่อมกับ source ที่ retrieve ได้จริง
AI-05 ห้ามสร้าง page number, citation หรือข้อความกฎที่ไม่มีใน context
AI-06 ถ้าค้นไม่พบ ให้บอกว่าไม่พบหลักฐานเพียงพอและเสนอคำค้นที่เกี่ยวข้อง
AI-07 GM assistant ช่วยอธิบาย rule/scene, แนะนำ skill และสรุปการเตรียมได้
      ส่วนที่เป็น recommendation ต้องติดป้าย
AI-08 Treat retrieved/scanned text as data ไม่ใช่คำสั่งที่เปลี่ยน system policy
AI-09 AI ไม่มีสิทธิ์เปลี่ยน game state โดยตรง; ข้อเสนอผ่าน domain action,
      permission และผู้ใช้ยืนยันเมื่อมีการนำไปใช้
AI-10 Gemini API key อยู่ Script Properties และไม่ถูกส่งให้ browser
AI-11 มี timeout/retry/backoff/rate limits ที่เหมาะสม พร้อม graceful failure
AI-12 หาก Gemini ใช้ไม่ได้ campaign/character/session ที่ไม่พึ่ง AI ยังใช้ได้
AI-13 แสดงว่าข้อความ/ภาพใดถูกส่งไป AI; ส่งเฉพาะบริบทจำเป็นของ request
AI-14 Cache key ต้องรวม source version, language, campaign/visibility scope
      และปัจจัย permissions ที่จำเป็น ห้ามตอบ cached GM answer ให้ Player
AI-15 AIHistory มี user/campaign/session, question, answer type, source refs,
      timestamp, visibility และ model version; ห้าม log API key/token

18. Data Dictionary และ Google Sheets Structure

กติกากลาง:
- ID ไม่เปลี่ยนเมื่อแก้ชื่อ และต้อง unique
- Datetime เก็บรูปแบบมาตรฐานเดียว เช่น ISO-8601 UTC และแสดงตาม timezone
- ทุก mutable record มี CreatedAt, UpdatedAt, Version; เพิ่ม actor เมื่อจำเป็น
- Monetary values ใช้หน่วยย่อยแบบ integer หากจำเป็นเพื่อหลีกเลี่ยง rounding
- ข้อมูลเขียนลง Sheet ต้องไม่ถูกตีความเป็น formula จากข้อความผู้ใช้
- ระบุ columns/required fields/enum/foreign keys ใน schema จริงของแต่ละ STEP
- Sheets ไม่ได้ enforce FK เอง; repository/domain layer ต้องตรวจ
- รายการต่อไปนี้เป็น logical minimum; developer เสนอ normalization เพิ่มได้

21. Non-functional Requirements
======================================================================

NFR-01 Security: backend authorization ครบทุก endpoint รวม search/AI/files
NFR-02 Privacy: raw Sheet, Corebook, GM notes และ scans ไม่เปิดสาธารณะ
NFR-03 Persistence: ปิด browser/login ใหม่แล้วยังอ่านข้อมูลเดิมได้
NFR-04 Reliability: network retry ไม่ทำให้ roll/XP/items/session จบซ้ำ
NFR-05 Performance: batch reads/writes, indexed lookup, scoped cache,
       pagination และ incremental refresh
NFR-06 Quota: ตรวจ current platform limits และออกแบบ batch/checkpoint
       ห้าม hardcode ตัวเลข quota จากความจำหรืออ้างใช้งานได้ไม่จำกัดจริง
NFR-07 Recovery: มี backup/export และ restore procedure ที่รักษา IDs/permissions
NFR-08 Maintainability: versioned schema, non-destructive migrations,
       environment config และแยก domain modules
NFR-09 Accessibility: readable contrast, touch targets, keyboard/focus,
       labels และไม่ใช้สีอย่างเดียว
NFR-10 Observability: error logging พร้อม request ID โดยไม่เปิดเผย secrets
NFR-11 Copyright: private companion; ไม่ทำ public PDF download, public
       rulebook dump หรือ public artwork redistribution
NFR-12 AI resilience: ใช้แอปพื้นฐานต่อได้เมื่อ AI unavailable/quota exhausted

PROPOSED performance targets เพื่อใช้วัดและปรับหลัง prototype:
- Dashboard ที่มี cache: p95 ไม่เกิน 5 วินาที ภายใต้ test workload ที่ตกลง
- Mutation ทั่วไปที่ไม่ใช้ AI: p95 ไม่เกิน 5 วินาที
- Live state refresh ระหว่างเล่น: ช่วงประมาณ 5–10 วินาทีแบบปรับได้
- AI/scan: แสดง processing/progress และ timeout ที่กำหนด; ไม่รับประกันเท่ากัน
ตัวเลขข้างต้นเป็นเป้าหมายทดสอบ ไม่ใช่คำรับประกันของ Apps Script
กำหนดจำนวน concurrent users, records และอุปกรณ์ก่อนทดสอบ performance จริง

23. Development Roadmap และ Gates
======================================================================

Phase 1 Foundation
GitHub repository/Codespaces setup, App shell, configuration, Users,
Google Login, identity verification, CI checks (ถ้าเลือกใช้) และ
permission infrastructure
Gate: ผู้ใช้สองบัญชี login ผ่าน deployment จริง; identity spoofing ถูกปฏิเสธ

Phase 2 Corebook Database
Import/index, entities, rule verification register, translations structure
Gate: sample source citations เปิดตรงหน้า, GM content ถูก classify,
mechanical rules ที่จะใช้ใน phase ถัดไปผ่าน verification

Phase 3 Campaign
My Campaigns, Create, Invite, Join, Roles, dashboards
Gate: ทดสอบ A/B/C accounts และ cross-campaign isolation ผ่าน

Phase 4 Character Creator
Background, Personality, Archetype, Skills, Knacks, Equipment,
Starting Package, validation, Submit/Approval
Gate: valid/invalid build, budget, GM-only approval, permission exceptions ผ่าน

Phase 5 Investigator Sheet
Character data/resources/live state, injury/trauma/effects
Gate: เปลี่ยนภาษาหรือเปิดใหม่ไม่เปลี่ยน/สูญเสีย state

Phase 6 Sessions
Create, Attendance, Start/Pause/Resume/End, snapshot/history พื้นฐาน
Gate: จบ Session 1 แล้วเริ่ม Session 2 ใช้ character เดิมและอ่านอดีตได้ถูกต้อง

Phase 7 Play System
Dice engine, live state mutation, roll history, synchronization
Gate: verified game scenarios, concurrent roll, duplicate retry และ stale write ผ่าน

Phase 8 Rulebook & AI
Bilingual search, role-aware retrieval, grounded answers, citations
Gate: known-answer/no-source/spoiler/prompt-injection/cache-isolation tests ผ่าน

Phase 9 GM Tools
Scenes, NPCs, Enemies, Locations, Clues, Handouts, Visibility
Gate: hidden/revealed/selected-player data ถูกต้องทั้ง API และ files

Phase 10 Scanner
Camera, upload, extraction, translation, review, material library
Gate: source traceability, OCR correction และ private upload ผ่าน

Phase 11 Campaign Journal
Expanded timeline, summaries, XP/character history, export/restore
Gate: restore sample Campaign รักษา IDs/links/permissions และ history ได้

Phase 12 Polish
Mobile/tablet, accessibility, performance, quota behavior, errors,
setup documentation และ regression review
Gate: MVP acceptance tests ทั้งหมดผ่านใน target deployment

แต่ละ Phase แบ่งได้หลาย STEP; ต้องตรวจ prerequisite ก่อนเริ่ม
ไม่จำเป็นต้องรอ Phase 11 จึงค่อยเก็บ events/snapshots: โครงสร้างประวัติต้อง
เริ่มตั้งแต่ feature ที่สร้างข้อมูล เพื่อไม่สูญเสียอดีตที่สร้างไปแล้ว

24. Acceptance Test Matrix
======================================================================

AT-01 Authentication
Given ผู้ใช้ไม่มี session ที่ตรวจแล้ว
When เรียก campaign endpoint
Then ไม่ส่ง campaign data และแจ้งให้ login

AT-02 Campaign Isolation
Given A เป็น GM Campaign X แต่ไม่เป็นสมาชิก Y
When ส่ง CampaignID/ObjectID ของ Y
Then ถูกปฏิเสธ แม้ A จะเป็น GM ใน X

AT-03 Invite Identity
Given invite สำหรับ B
When C เปิด/ตอบรับ invite
Then C ไม่ได้เป็น member; B ใช้ verified account จึงตอบรับได้

AT-04 Spoiler Protection
Given NPC/clue มี GM secret
When Player โหลด dashboard/search/AI/translation/export/file
Then ไม่มี secret ใน response, context, cache หรือ file access

AT-05 Character Ownership
Given Player A และ B มี characters คนละตัว
When A ส่ง mutation ของ B
Then ถูกปฏิเสธ รวมการปลอม OwnerUserID ใน payload

AT-06 Character Validation
Given rules ที่ VERIFIED แล้ว
When เลือก skills/knack/equipment/starting package ผิดกฎ
Then server ปฏิเสธพร้อมเหตุผลและ source reference

AT-07 GM Approval
Given build ต้องขอ permission
When Player Submit
Then ยังไม่ Ready จน GM อนุมัติ และ Player อนุมัติตนเองไม่ได้

AT-08 Language Independence
Given GM ใช้ en และ Player ใช้ th
When เปลี่ยนภาษา
Then character IDs, pool, XP, items, rolls และ session state คงเดิม

AT-09 Continuity
Given Session 1 จบพร้อม injuries/items/XP
When เริ่ม Session 2
Then ตัวละครเดิมต่อเนื่อง และ snapshot Session 1 ไม่เปลี่ยนเมื่อเล่น Session 2

AT-10 Attendance
Given สมาชิกไม่ได้มา Session นี้
When GM บันทึก attendance
Then membership ยังอยู่; snapshot บันทึกเฉพาะผู้ที่เข้าร่วมตามจริง

AT-11 Dice Source Accuracy
Given ชุดตัวอย่าง/edge cases จาก Corebook ที่ตรวจแล้ว
When คำนวณ roll/horror/pool/damage
Then ผลตรงกฎ พร้อม source และ rule version

AT-12 Duplicate Mutation
Given request ID เดิมของ roll, XP purchase หรือ end-session
When retry สองครั้ง
Then ได้ผลเดิมและเกิดผลทาง mechanics เพียงครั้งเดียว

AT-13 Concurrent Editing
Given สองอุปกรณ์อ่าน character version เดียวกัน
When ส่ง mutation ที่ขัดแย้ง
Then ไม่เสีย XP/pool หรือ overwrite เงียบ; server resolve/reject อย่างชัดเจน

AT-14 AI Grounding
Given คำถามที่มี/ไม่มี source
When Ask Rule
Then คำตอบที่อ้าง official มี source จริง หรือบอกว่าหาหลักฐานไม่พบ

AT-15 Selected Reveal
Given clue เผยให้ Player A เท่านั้น
When A/B ดูข้อมูล
Then A เห็นและ B ไม่เห็น รวม search, translations, AI และ files

AT-16 Revocation
Given member ถูก REMOVED หรือ role ลดลง
When request ถัดไปใช้ session เดิม
Then server บังคับ permission ใหม่ ไม่เชื่อ role cache เก่า

AT-17 Service Failure
Given Gemini/Drive/network ชั่วคราวล้มเหลว
When ใช้ฟีเจอร์ที่เกี่ยวข้อง
Then แสดง error/retry ไม่สูญเสียข้อมูลที่ commit แล้ว และไม่ส่งผลซ้ำ

AT-18 Snapshot Failure Recovery
Given end-session ล้มเหลวกลาง multi-sheet operation
When retry/recover
Then snapshot, XP และ session status สอดคล้องและไม่มี duplicate award

AT-19 Rule Visibility
Given Player คลิก View Original ของ player rule
Then ไม่ได้ full-book access ที่เผย GM-only content โดยไม่ตั้งใจ

AT-20 Restore and Migration
Given backup/test dataset เวอร์ชันก่อนหน้า
When restore/migrate ตามคู่มือ
Then IDs, foreign keys, permissions, history และ canonical language คงถูกต้อง

25. Deliverables และ Definition of Done
======================================================================

ทุก STEP ส่งมอบ:
1. วัตถุประสงค์และขอบเขตที่ทำในรอบนี้
2. รายชื่อไฟล์ที่ Codex สร้าง/แก้ พร้อมสรุปการเปลี่ยนแปลง
3. Google Sheets schema/column changes และ migration ที่ไม่ลบข้อมูลเดิม
4. Script Properties/Codespaces Secrets/config ที่ต้องตั้ง โดยใช้ชื่อ key และ
   placeholder เท่านั้น ห้ามพิมพ์ค่าจริงของ secret
5. OAuth/deployment/scopes ที่จำเป็น พร้อมเหตุผลและขั้นตอน
6. วิธีเปิด Codespace, ติดตั้ง dependencies และรัน setup/test ทีละข้อ
7. Test procedure และ expected results
8. ผลทดสอบที่ Codex รันได้จริง พร้อมแยกสิ่งที่ต้องให้ผู้ใช้ทดสอบใน Google
9. Known limitations, unresolved questions และ rollback/recovery เมื่อจำเป็น
10. Progress record: STEP ปัจจุบัน, completed, pending, source rules verified
11. สรุป diff และสถานะ Git; ห้ามอ้างว่า commit/push/deploy แล้วหากยังไม่ได้ทำ

แนะนำแยกไฟล์/โมดูลตามหน้าที่ เช่น Config, Auth, Permissions, Repository,
Campaigns, Characters, Sessions, Rules, Dice, AI, Materials และ UI
ชื่อไฟล์จริงให้ตกลงตามโครงสร้าง Apps Script; อย่ารวมทุกอย่างไว้ในไฟล์เดียว

Definition of Done ของ feature:
- ใช้งานได้จาก UI ถึง persistence จริง
- server validation/permission ครบ
- ไม่มี secrets รั่วใน response/log/client
- รองรับ success/loading/error และ retry ที่เกี่ยวข้อง
- มี source verification สำหรับ game mechanics
- ผ่าน acceptance tests ที่สัมพันธ์กับ feature
- คู่มือติดตั้งตรงกับโค้ดที่ส่ง
- ไม่ทำลาย feature ที่ผ่านการทดสอบแล้ว

26. Open Decisions ก่อนลงมือส่วนที่เกี่ยวข้อง
======================================================================

OD-01 Google deployment/auth flow ที่ใช้ได้จริงกับบัญชี GM และ Players
OD-02 Storage ownership: owner-centralized ตามข้อเสนอ หรือแยก GM-owned storage
OD-03 จำนวน concurrent players/campaigns และ dataset สำหรับ performance test
OD-04 ขอบเขต Co-GM และสิทธิ์ private notes ตาม default ที่ระบุ
OD-05 จำนวน active investigators ต่อ Player/Campaign และการ retire/replacement
OD-06 Campaign timezone และการนับ session date
OD-07 Co-GM/Player เห็น Investigator คนอื่นระดับใดใน party overview
OD-08 Gemini model/config และขอบเขตข้อมูล private ที่อนุญาตให้ส่งเพื่อประมวลผล
OD-09 Email notification ของ invitation จะเปิดหรือใช้ in-app ก่อน
OD-10 Official rules ที่ยัง NEEDS_VERIFICATION รวม page mapping และ edition
OD-11 การใช้ custom rules/allowed sources และ policy เมื่อ source ขัดแย้ง
OD-12 ผู้ดูแลการตรวจ OCR/translation/rule verification และขั้น approve source
OD-13 GitHub repository และ Codespaces เป็นค่าเริ่มต้นตาม brief นี้;
      ชื่อ repository, visibility และ branch policy ให้ผู้ใช้เลือกตอน setup

ให้ถามเฉพาะ decision ที่ขัดขวาง STEP ปัจจุบันจริง
เรื่องที่ใช้ proposed default ได้ให้ระบุ assumption ชัดเจน ไม่หยุดทั้งโปรเจกต์
ห้ามใช้คำตอบที่ยังไม่มีเป็นเหตุให้เดากฎเกมหรืออ้างว่าระบบปลอดภัยแล้ว
